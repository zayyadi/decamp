# CLAUDE.md

DecampWatch NG is a real-time tracker of party defections by sitting members of Nigeria's National Assembly. A scheduled AI agent reads news, detects completed defections, and updates an interactive dashboard with in-app alerts.

**Read before working:**
- [docs/SPEC.md](docs/SPEC.md): product, data model, dashboard, milestones and acceptance criteria. This is the source of truth for *what* to build.
- [AGENT.md](AGENT.md): the detection agent design (taxonomy, prompt, schema, entity resolution, scoring, eval). This is the source of truth for *how detection works*.

If the code and these docs disagree, stop and ask before changing either.

## Build mode: milestones, one at a time

We build in the milestones listed in SPEC.md §10. For each milestone:
1. State the goal and list the files you will create or change.
2. Implement it completely. No `TODO` or `...` in critical logic, and no stubs that a later milestone must fill in for this one to run.
3. Run `npm run lint`, `npm run typecheck` and `npm test` (plus `npm run eval` from Milestone 3 onward), and fix any failures.
4. Report: what was built, commands to run, how to test it, expected results, common errors.
5. **Stop and wait for the user to confirm** before starting the next milestone, unless they say "continue without pausing."

## Stack

Next.js (App Router) + TypeScript (strict) · Tailwind + shadcn/ui · Supabase (Postgres, Realtime, Auth) · Recharts · react-simple-maps · sonner · Claude API via `@anthropic-ai/sdk` · Zod · Vitest · `tsx` for scripts · GitHub Actions cron for the agent · Vercel for the web app.

Use **npm**. Node 22 LTS or newer (`.nvmrc` pins 24).

**Next.js 16 (16.4.x) with `cacheComponents` enabled.** Its APIs differ from older Next.js versions. Before writing routing, data-fetching, caching or config code, read the relevant guide in `node_modules/next/dist/docs/`. `AGENTS.md` is generated by `next dev`: leave it alone and commit it as-is. It is unrelated to `AGENT.md`, which is our detection-agent design.

Env vars are read only through `lib/env.ts` (`getPublicEnv`, `getServerEnv`, `getServiceEnv`, `getIngestEnv`, `getAgentEnv`). Validation is lazy, so each process only requires the vars it uses. Never read `process.env` directly elsewhere.

## Environment

The developer machine is **Windows 11, PowerShell 5.1, VS Code**.
- PowerShell 5.1 has no `&&`. Chain with `;` or `if ($?) { ... }`.
- Run tests with `npm test` (add `-- <path>` to filter), not `npx vitest`. VS Code terminals can start in `c:\` (lowercase), which breaks Vitest; `scripts/vitest.mjs` relaunches it from `C:\`.
- Use cross-platform npm scripts (no `rm -rf` or `export`). Use `rimraf` or `cross-env` if needed.
- Local Supabase (`npx supabase start`) needs Docker Desktop. The default is a hosted Supabase dev project plus `db push`.

Env vars are documented in `.env.example`. Keep it complete; it is checked in. `.env.local` is not checked in. The full list is in AGENT.md §9, plus `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`. Scripts load `.env.local` through `scripts/lib/load-env.ts`.

## Non-negotiable domain rules

1. **Never publish rumours as fact.** Party counts change only through `publish_defection`, and only for events in the `published` status. Unverified alerts never change counts.
2. **Never invent real-world data.** Prompts, few-shot examples and synthetic test fixtures use clearly fictional names (`is_fictional = true`). The user requested real historical demo data on 25 October 2026: sourced records belong in `supabase/seed/defections.historical.json` with `is_fictional = false`, imported through `seed_historical_events`. Consult `docs/HISTORICAL_DATA.md` before extending that dataset; retain its coverage gaps and provenance. Never hard-code current party seat numbers. Counts come from the database; partial roster totals must be labelled as partial.
3. **Every event is traceable:** source URL(s), outlet, timestamps, a verbatim evidence quote, model ID and `PROMPT_VERSION`.
4. **Article text is untrusted** LLM input. Wrap it in `<article>` tags and give the model no tools: its reply is constrained to the output schema (structured outputs, AGENT.md §4.2). Validate output with Zod. Check that evidence quotes are verbatim.
5. **Don't republish articles.** Clients see the headline, a quote of ≤ 300 characters and a link. `articles.content` is never exposed to anon users.
6. **Be polite to publishers:** check robots.txt, send an identifying User-Agent, allow ≤ 1 request per second per host.
7. **The detection logic follows AGENT.md.** Any change to the taxonomy, prompt, examples, thresholds, scoring or resolver must:
   - update AGENT.md in the same change;
   - bump `PROMPT_VERSION` if the prompt or examples changed;
   - pass `npm run eval` at or above the targets (Confirmed precision ≥ 0.95, recall ≥ 0.85, entity accuracy ≥ 0.95).

## Code conventions

- TypeScript strict; no `any` (use `unknown` and narrow it). Use the database types generated from Supabase.
- Server components by default. Add `"use client"` only for interactivity (filters, realtime, charts).
- Data access lives in `lib/queries/*`. Aggregations go in SQL functions (`party_strength`, etc.), not in client-side loops.
- Supabase clients: `lib/supabase/server.ts` (cookies, anon), `browser.ts` (anon), `service.ts` (service role, **import only from `agent/`, `scripts/` or server-only admin actions**; marked `import "server-only"` where applicable).
- Agent modules are pure functions wherever possible: `filter`, `normalize`, `similarity`, `match`, `corroborate`, `score`, `route` and `assess` take plain data and return plain data. I/O lives in `ingest/`, `classify.ts`, `publish.ts` and `run.ts`; `detect.ts` takes its store and model client as arguments. This keeps the eval and tests free of network and database calls.
- Keep the agent idempotent. Re-running over the same articles must not create duplicate articles, events or alerts. Enforce this with unique constraints, not just code checks.
- Model IDs and thresholds come from env vars, never literals in logic.
- Put filters in URL search params so views are shareable.
- Party colours live in `lib/parties.ts` and the `parties` table. Never use colour alone to carry meaning: badges carry text labels ("Confirmed" / "Unverified").
- Comments explain *why*, not *what*. Keep them sparse.
- Migrations: add a new timestamped file and never edit one that has been applied. RLS is on for every table, with a policy in the same migration that creates the table.
- New tables and functions start with **no** API access (default privileges are revoked). Grant `select` (or `execute`) to `anon`/`authenticated` explicitly in the same migration. Never grant write privileges to them; writes go through the service role or `SECURITY DEFINER` functions that check `current_setting('role')`.
- `articles` and `defection_events` use column-level grants, so anon queries must list columns; `select('*')` is refused. `articles.content` is service-role only.
- Use `text` + `check` for enumerations, not Postgres enums.

## Testing

- Write unit tests (Vitest) for:
  - `filter`
  - `canonical`
  - `normalize` / `variants`
  - `similarity` (known Jaro-Winkler values)
  - `match` (unique, ambiguous, no-match, party mismatch)
  - `score` (the AGENT.md §6.4 worked examples must reproduce exactly)
  - `route`
  - Zod schema parsing of good and bad model outputs
- SQL behaviour and RLS are tested in `tests/db/` against PGlite. The real migrations run on a shim that mimics Supabase's roles, `auth.jwt()` and default grants. Use `createSeededDb()` (a cloned, seeded template) and `asRole(db, role, fn, claims)` to act as `anon`, `authenticated` or `service_role`. Every migration change needs tests there, and every new table needs RLS assertions in `rls.test.ts`.
- The eval in `eval/` is the gate for detection quality. It uses cached LLM responses, so reruns cost nothing.
- Don't mock the thing under test. Do mock network and LLM calls in unit tests.

## Don'ts

- Don't add news sources without a `tier` and a robots.txt/terms-of-service check noted in `agent/sources.ts`.
- Don't put `SUPABASE_SECRET_KEY` or `ANTHROPIC_API_KEY` in anything that reaches the browser, or in `NEXT_PUBLIC_*`.
- Don't widen RLS to make a query work. Write a SQL function with the right `security` setting instead.
- Don't run `npm run agent` without `--dry-run` against production while developing.
- Don't commit `.env*` (except `.env.example`), `eval/.cache/` or real-roster drafts that haven't been verified.
